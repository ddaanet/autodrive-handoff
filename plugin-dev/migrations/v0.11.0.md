# Migrating to 0.11.0

0.11.0 adds two opt-in pieces for a plugin's own `precommit`: gate sentinels,
which let a gate skip itself when the files it reads have not changed, and a
quiet bats runner. **Neither changes anything for a plugin that does not adopt
it.** `release.just` is untouched, `precommit` and `prerelease` keep their
contract, and the two new files, `gates.just` and `run-bats.sh`, are only used
by a justfile that imports them. The manual chapter is
`plugin-dev/manual/gates.md`.

Two other changes apply to every plugin on the pull, and need no step unless
the first bites:

- **The release's clean-tree check no longer exempts `.claude/`.** Only the
  gitlore memory submodule is exempt. A tracked file under `.claude/` that
  differs from HEAD, such as `.claude/settings.json`, now refuses `just release`
  and `just resume-release`, and the refusal names it. Commit the change first.
  Untracked and gitignored files were never in the check.
- **A session launched before the first `just dogfood` now loads the copy**
  after `just dogfood` and `/reload-plugins`, with no relaunch. See
  `plugin-dev/manual/dogfood.md`.

Take the steps below to adopt them. A plugin that already carries gitlore's
copies skips to [gitlore](#gitlore). Do the conversion as its own commit,
separate from the subtree-pull merge.

## 1. Import the prolog

In `justfile`, beside the existing import:

```just
import 'plugin-dev/release.just'
import 'plugin-dev/gates.just'
```

Run `just --list` to confirm the justfile still compiles. `gates.just` defines
one private variable, `plugin_dev_gate_prolog`; a justfile of your own that
already uses that name is the only conflict.

## 2. Choose the inputs

The gate caches its verdict against a hash of the files you name, and is correct
only while every check in the recipe reads inside them. A check that reads a
path the hash ignores goes red on an unrelated commit, days after the file that
broke it was added, with nothing to say why. So decide the list before touching
the recipe.

1. Write down every check the recipe runs and the paths each one reads. A
   linter with no path argument reads the whole project; `claude plugin
   validate` reads `skills/` and `hooks/`; a bats suite reads what it sources.
2. Make the list the union of those paths, plus the ones nearly every plugin
   needs. The guard already hashes the justfile and `plugin-dev` for every
   gate, apart from your list, so the gate's commands and a toolkit update each
   invalidate the pass and an exclude of yours cannot remove them; the rest are
   yours to list:
   - any justfile the root `justfile` imports;
   - lockfiles and tool configuration the checks read: `uv.lock`,
     `pyproject.toml`, `package-lock.json`, `.shellcheckrc`;
   - `.gitignore`, which decides which untracked files are hashed;
   - `.claude-plugin`, and `.claude/settings.json` if a check reads it.
3. Where a check reads more than you want it to, narrow the check (give it a
   path argument or an exclude) rather than widening the list. Where a cheap
   check reads outside the list of an expensive gate, move it to a recipe of its
   own with its own list.
4. **A gitlink cannot be hashed.** If a check reads a submodule, such as a
   gitlore `memory/` mount, the hash sees only the path's name: an edit inside
   it, and a new commit of it, move nothing. Do not list it. Run that check
   **uncached, ahead of the guard**, in the recipe body, so it runs on every
   `just precommit` including the one that edits what it reads. The same goes
   for a check over a tree you leave out on purpose, such as a docs-link checker
   over `docs/`.

Name paths; do not hash `.`. Naming keeps scratch directories, build output and
the sandbox's phantom home dotfiles out of the hash. A path that matches no file
is refused at the guard, so a typo cannot cache forever.

## 3. Turn the recipe into a shebang recipe

A plain recipe becomes a shebang recipe that opens with the prolog. Before:

```just
precommit: format-docs
    scripts/check-memory-hygiene.sh
    jq . .claude-plugin/plugin.json > /dev/null
    shellcheck scripts/*.sh
    bats tests/*.bats
```

After:

```just
precommit: format-docs
    #!{{ plugin_dev_gate_prolog }}
    scripts/check-memory-hygiene.sh
    sentinel-guard precommit .claude-plugin scripts tests
    jq . .claude-plugin/plugin.json > /dev/null
    shellcheck scripts/*.sh
    plugin-dev/run-bats.sh tests/*.bats
    record-sentinel
```

What changed:

- The first body line is `#!{{ plugin_dev_gate_prolog }}`. It must be first.
- `sentinel-guard <gate> <pathspec>...` comes next, after any check that has to
  run uncached (here the memory checker, which reads a gitlink). The gate name is
  the recipe name; it keys the sentinel file. When the inputs are unchanged the
  guard prints `<gate>: cached (inputs unchanged)` and ends the recipe with
  status 0, so nothing below it runs.
- `record-sentinel` is the last line. It runs only if every check above it
  passed, because the body is a script under `set -euo pipefail`.

A shebang recipe is one bash script, not a line per command. just no longer
echoes each line before it runs, a leading `@` on a line means nothing, an
unset variable is an error, and `{{ }}` is still interpolated by just. A
dependency (`precommit: format-docs`) runs first and every time, as before.
`prerelease: precommit` stays as it is.

**One guard per recipe body.** The guard leaves shell variables for
`record-sentinel`, so a second gate in the same body would clobber the first's.
The prolog refuses it (`each gate needs its own recipe`). A plugin with several
gates gives each its own recipe, guard and list, and has `precommit` depend on
them:

```just
precommit: check-distribution lint test
```

The sentinels live under the gitdir (`.git/plugin-dev/gates/`), so they are not
in `git status` and need no `.gitignore` entry. Each clone and worktree has its
own.

## 4. Fold in tool versions

If your checks use tools no lockfile in the list pins (`bats`, `shellcheck`,
`jq`, `python3` from the system), a tool upgrade should invalidate the pass.
Export one version command per line from the justfile:

```just
export PLUGIN_DEV_GATE_TOOLS := "bats --version\nshellcheck --version\njq --version"
```

Empty by default: if you set nothing, no tool is hashed. Tools pinned through
`uv.lock` or a similar file in the list need no entry. A listed command that
fails or is missing makes the hash uncomputable, and the run says so
(`could not hash inputs; the pass was NOT recorded`) instead of caching.

## 5. Swap `bats` for the quiet runner

Replace each direct `bats …` call in the gate with `plugin-dev/run-bats.sh …`;
it takes the same arguments, bar any that change the output format or print
something other than test results (`-p`, `-F` with a formatter other than `tap`
or `tap13`, `-c`, `-v`, `-h`), since it reads TAP. A green run prints one line,
`bats: N passed, 0 failed`, and leaves no log; a red one prints the failing
tests with their diagnostics and the same line followed by
`— full log: <path>`, the log it kept.
It exits with bats' own status, or 1 when bats exited 0 having run no test, and
needs no sentinels: use it in a recipe that does not cache.

## 6. Prove the coverage, and know how to force a run

Do not trust the list because it reads right. Run `just precommit` twice and
expect `precommit: cached (inputs unchanged)` the second time. Then append a
throwaway line to a file in each tree your checks read, confirm the next run does
real work, remove the line and confirm `git diff` on that file is empty. Edit a
file you left out and confirm the gate stays cached.

To run the checks whatever the sentinels say, as before a release:

```sh
PLUGIN_DEV_GATE_FORCE=1 just precommit
```

A forced run still records its result. `PLUGIN_DEV_GATE_DIR=<dir>` keeps the
sentinels in `<dir>` instead, for a test that drives the real recipe with its
checks stubbed out, so that a pass recorded from it cannot overwrite the real
one.

## gitlore

gitlore already carries its own copies of both pieces: the sentinel functions in
the `bash_prolog` variable of its `justfile`, and `scripts/run-bats.sh`. Replace
them with the toolkit's, and keep what the toolkit does not ship, `run-suites`
and its per-suite cache (`scripts/run-bats-cached.sh`,
`scripts/parse-bats-junit.py`), exactly as it is.

1. Import the prolog beside `plugin-dev/release.just`:

   ```just
   import 'plugin-dev/gates.just'
   ```

2. Rebuild `bash_prolog` from the toolkit's prolog. Delete `check-sentinel`,
   `sentinel-guard`, `record-sentinel` and `gate-inputs-hash` from it, and keep
   `run-suites` and its comment. `run-suites` reads `sentinel_dir`,
   `gate_inputs` and `gate-inputs-hash`; the toolkit's prolog sets and defines
   the same, so it works unchanged.

   ```just
   [private]
   bash_prolog := plugin_dev_gate_prolog + \
       ( if trace == "true" { "set -x\n" } else { "" } ) + '''
   # run-suites () { … } and its comment, unchanged, as it stands today.
   '''
   ```

   The toolkit's prolog opens with its own `set -euo pipefail`, so the old
   `set -xeuo pipefail` switch becomes the extra `set -x` line above.

3. Move the tool versions out of `gate-inputs-hash` into the exported variable,
   one command per line, keeping the reason for `python3` in a comment above it:

   ```just
   export PLUGIN_DEV_GATE_TOOLS := "bats --version\nshellcheck --version\njq --version\npython3 --version"
   ```

4. Rename the environment variables and the sentinel directory. `grep -rn
   'GITLORE_GATE\|gitlore/gates' .` outside `plans/` and `memory/` finds the
   places; the ones known are `justfile` (comments), `scripts/run-bats-cached.sh`,
   `scripts/lint-shell.sh`, `tests/justfile_gates.bats`, `README.md` and
   `CLAUDE.md`:

   - `GITLORE_GATE_DIR` becomes `PLUGIN_DEV_GATE_DIR`;
   - `GITLORE_GATE_FORCE` becomes `PLUGIN_DEV_GATE_FORCE`;
   - `.git/gitlore/gates` becomes `.git/plugin-dev/gates`.

   `GITLORE_TEST_JOBS` stays, since `run-suites` stays. The per-suite cache
   files follow `sentinel_dir`, so they move to the new directory with it.

5. Replace `scripts/run-bats.sh` with `plugin-dev/run-bats.sh`, and delete the
   old file. `grep -rn 'run-bats\.sh' .` outside `plans/` finds the callers: the
   `check-distribution` recipe in `justfile`, `scripts/run-bats-cached.sh`
   (`"$script_dir/run-bats.sh"`), `scripts/mutate-and-run.sh`
   (`"$here/run-bats.sh"`), `scripts/test-macos.sh`, `CLAUDE.md`, and the
   `tests/bsd_portability.bats` test that runs it under a BSD `mktemp` stub.
   Repoint each at `plugin-dev/run-bats.sh`, relative to where it sits. The log
   prefix is now `plugin-dev-bats.`; `gitlore-bats-junit.` is the cached
   runner's own and stays.

6. The toolkit's functions are stricter than the copies. `check-sentinel` and
   `sentinel-guard` need a gate name and at least one pathspec, take a plain name
   (no `/`), exit if a second gate follows the first in one body, and
   `record-sentinel` exits when no guard ran. The guard also hashes the justfile and
   `plugin-dev` beside the pathspecs and refuses one that matches no file; a
   caller of `gate-inputs-hash` that sets only `gate_inputs`, as `run-suites`
   does, still gets both. Run
   `bats tests/justfile_gates.bats` and fix what the renames and these refusals
   break. The tests there that assert the sentinel functions' own behaviour now
   duplicate the toolkit's suites and may go; the ones that assert gitlore's
   recipes are wired to them stay.

7. Delete the old sentinels. Those under `.git/gitlore/gates` are never read
   again and are safe to remove:

   ```sh
   rm -rf "$(git rev-parse --git-path gitlore/gates)"
   ```

   The first `just precommit` after the change runs every gate once, since
   nothing is recorded under `plugin-dev/gates` yet.

Then run `just precommit` twice, and expect each gate to say
`cached (inputs unchanged)` the second time.
